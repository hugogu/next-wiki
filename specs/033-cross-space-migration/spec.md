# Feature Specification: Cross-Space Page Migration

**Feature Branch**: `codex/033-cross-space-migration`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "支持将一个页面或文件夹在不同space之间的迁移，入口包括Navigator Pane, Pages列表以及OpenAPI/MCP。像之前用wiki.js import功能导入的页面，不少就是AI Generation的直接放Wiki也不太合适。"

**Depends on**: 005-content-import-export (Wiki.js import provenance), 022-llm-wiki-mode (content spaces and generated-content rules), 032-space-publication (canonical space routes and visibility).

## Summary

Administrators can refile one page or an entire folder subtree between the Wiki and AI Generation spaces, without recreating content. This makes it practical to correct the placement of imported material — for example, moving Wiki.js pages that were originally AI-generated into the AI Generation space.

The same migration behavior is available from the Navigator Pane, the Pages list, the documented external interface, and MCP. A migration retains durable page identity, prior revisions, authorship, safe import provenance, and audit history. It applies the destination space's content rules without claiming that an imported page was generated by a particular model or person.

Raw source material is intentionally excluded from cross-space migration in this release. Its append-only and evidence-preservation rules remain intact.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Refile an Imported AI Page (Priority: P1)

As an Administrator, I want to move an imported page from Wiki to AI Generation, so that the knowledge base accurately distinguishes ordinary wiki material from AI-created content without copying it or losing its history.

**Why this priority**: Correcting imported content placement is the immediate user need and provides value with a single-page move.

**Independent Test**: Create a published Wiki page with imported provenance, move it to AI Generation, and verify that the source-space listing no longer contains it while the destination listing, page history, safe provenance, and canonical page address identify the same page.

**Acceptance Scenarios**:

1. **Given** an Administrator can manage a Wiki page and AI Generation is available, **When** they confirm a move to AI Generation, **Then** the page is removed from the Wiki location and appears once at the selected destination location with its stable identity and revision history retained.
2. **Given** a Wiki.js-imported page has no verified model-origin information, **When** it is moved to AI Generation, **Then** its imported source details remain available to authorized users and the system records that a user classified it as generated instead of inventing unsupported model provenance.
3. **Given** a page's content does not meet the destination's required generated-content structure, **When** the user confirms the move, **Then** the system shows the required adaptation before confirmation and retains the prior content revision as part of the page history.
4. **Given** the proposed destination would make a currently restricted page more widely readable, **When** the move is submitted without an explicit visibility choice, **Then** the page remains at least as restricted as it was before the move.

---

### User Story 2 - Move a Folder as One Organized Unit (Priority: P1)

As an Administrator, I want to move a folder and all of its nested pages to another eligible space, so that a group of imported AI materials can be reclassified without repeating the same action page by page.

**Why this priority**: Bulk correction is the main efficiency gain for an imported hierarchy and remains valuable independently of external automation.

**Independent Test**: Move a folder containing nested pages, a page at the folder root, and a draft; verify that every selected item arrives below the chosen destination path, no source copy remains, and no unrelated page moves.

**Acceptance Scenarios**:

1. **Given** a folder path contains pages and nested folders, **When** the user chooses a destination space and folder and confirms the preview, **Then** every selected page keeps its relative path below that destination and the operation reports its completed item count.
2. **Given** the selected folder is also a page, **When** the folder move is completed, **Then** that page and its descendants move together unless the user explicitly excludes the root page before confirmation.
3. **Given** any destination path would collide with an existing page or another selected item after normalization, **When** the migration is previewed or confirmed, **Then** it identifies every conflict and makes no content change until the user resolves or excludes the conflicting items.
4. **Given** a folder migration has started, **When** the user leaves the page or their browser session ends, **Then** the migration continues safely and its eventual result, warnings, and per-item outcomes can be reviewed.

---

### User Story 3 - Start the Same Migration from Content Management (Priority: P2)

As an Administrator, I want an obvious migration entry from both the Navigator Pane and Pages list, so that I can reorganize content at the point where I discover it.

**Why this priority**: Both views serve different discovery workflows; their shared action prevents an administrator-only maintenance task from becoming a manual detour.

**Independent Test**: Open the same eligible page in both views as an Administrator, start a move from either entry, and verify that each opens the same destination, preview, permission, and confirmation experience.

**Acceptance Scenarios**:

1. **Given** an eligible page or folder is visible in the Navigator Pane, **When** an Administrator opens its contextual actions, **Then** they can start a cross-space migration without leaving the navigator context.
2. **Given** an eligible page is visible in the Pages list, **When** an Administrator selects its migration action, **Then** they receive the same migration form and outcome as from the Navigator Pane.
3. **Given** a user lacks permission for the source or destination, or the current writing mode does not make the destination available, **When** they view either entry, **Then** the action is unavailable or clearly explains why it cannot be used.
4. **Given** a migration completes, **When** the user returns to Navigator, Pages list, search, or a saved source-space link, **Then** each surface reflects the destination page once and uses its current canonical address.

---

### User Story 4 - Automate Reclassification Safely (Priority: P2)

As an Administrator-authorized integration or AI client, I want to preview and start a page-or-folder migration through the documented external interface and MCP, so that import clean-up can be automated using the same safeguards as the web experience.

**Why this priority**: Imported content can be extensive; safe automation avoids repetitive manual work while preserving the permission and audit model.

**Independent Test**: Use each programmatic entry to preview and execute a single-page and folder migration, then compare its result and audit record to the equivalent Navigator-initiated migration.

**Acceptance Scenarios**:

1. **Given** an integration has permission to move the selected content, **When** it requests a preview, **Then** it receives the destination mapping, affected-page count, required content adaptations, visibility impact, and all known conflicts before any content changes.
2. **Given** an integration or MCP client submits a valid confirmed migration, **When** the request is accepted, **Then** it receives a durable operation reference and can retrieve the current status and final per-item result.
3. **Given** a client is missing a required permission, supplies an ineligible Raw source or destination, or attempts an ambiguous destination, **When** it submits a preview or migration, **Then** it receives a clear refusal and no page is changed.
4. **Given** the public contract changes, **When** an external developer reads the published interface description, **Then** it can discover the migration inputs, permissions, states, outcomes, and error meanings without relying on web UI behavior.

### Edge Cases

- A user attempts to move a page to the space it already occupies, a deleted page, a translation child, a retired link, or an unavailable space: the request is refused without changing content.
- A page or folder changes after preview but before confirmation: the confirmation detects the changed selection or destination and requires a fresh preview rather than moving a different set of content.
- The selected folder is empty, contains only nested folders, or contains a mixture of published pages, drafts, and pages unavailable to the caller: the preview states the precise selection and eligibility outcome.
- The destination path is invalid, reserved, duplicates a selected path after normalization, or collides with an existing page: no selected item moves.
- A public page moves between spaces: its former public address redirects only when the moved page remains publicly eligible; otherwise it no longer discloses the page or its destination.
- A migration is retried after an interruption: completed items are not duplicated, and the result distinguishes completion, exclusion, conflict, and failure for every selected page.
- The request includes Raw as source or destination: it is refused because moving it would weaken the append-only evidence boundary.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST let an Administrator move one eligible page between Wiki and AI Generation spaces. This maintains the AI Generation space's existing administrator-curated authoring rule.
- **FR-002**: The system MUST let an authorized user select a folder subtree for cross-space migration, choose the destination folder, and preserve each moved page's relative path below it.
- **FR-003**: Before any move, the system MUST present a reviewable preview of the selected pages, source and destination locations, resulting paths, content adaptations, visibility effects, and all known conflicts.
- **FR-004**: A migration with unresolved path, normalization, permission, destination-policy, or selection-change conflicts MUST make no content changes. Users MUST be able to exclude eligible conflicting items and re-preview the remaining selection.
- **FR-005**: A successful migration MUST retain every moved page's durable identity, earlier revisions, authorship, created time, safe imported-source information, tags, and relationships. It MUST add an auditable migration record identifying the initiator, scope, source, destination, outcome, and any adaptation.
- **FR-006**: When a page enters AI Generation, the system MUST enforce that space's document-format and provenance requirements. If adaptation is necessary, it MUST be disclosed in the preview and represented as a new version without altering or erasing the prior version. Classification by a user MUST not be represented as verified model provenance.
- **FR-007**: A move MUST not automatically broaden readership. In the absence of an explicit authorized choice, the resulting visibility MUST be no less restrictive than the source page's visibility and must remain unpublished until a normal publication action occurs.
- **FR-008**: Raw content MUST NOT be accepted as a source or destination for this cross-space migration. The Raw space's append-only source-material and provenance guarantees remain unchanged.
- **FR-009**: The Navigator Pane MUST expose the migration action in contextual actions for eligible pages and folders. The Pages list MUST expose it for an eligible page. Both entries MUST use the same preview, confirmation, permission checks, and result semantics.
- **FR-010**: The system MUST make a completed move visible consistently in navigation, breadcrumbs, search, page lists, page relationships, revision views, and the canonical page address. It MUST not retain an active source copy.
- **FR-011**: For supported page-to-page references whose target is moved, the system MUST preserve or update the reference so authorized readers continue to reach the moved page. References it cannot safely resolve MUST be listed in the preview and final result without silently changing unrelated content.
- **FR-012**: A folder migration that cannot complete within an ordinary web interaction MUST continue independently of that interaction and provide a durable status, progress, cancellation state, per-item results, warnings, and retry information to the initiating user and other authorized reviewers.
- **FR-013**: The documented external interface MUST offer the same preview, confirmed migration, status, and result capabilities for both pages and folders. Its published contract MUST describe required permissions, inputs, result states, and actionable failures.
- **FR-014**: MCP MUST provide the same cross-space migration capability and return the same permission-safe preview and result information as the documented external interface.
- **FR-015**: Every browser, external-interface, and MCP request MUST enforce the same source and destination permissions, writing-mode availability, destination policies, and audit requirements. A caller may receive no title, path, provenance, or other information about content it cannot read.
- **FR-016**: The system MUST be idempotent for a retried confirmed migration: it must not create duplicate pages, duplicate revisions, or duplicate audit outcomes for pages already successfully moved by that migration.
- **FR-017**: Existing single-page cross-space moves MUST continue to work for eligible Wiki and AI Generation pages, now using the shared migration rules and result model.

### Public Content Delivery

- Moving a publicly readable page changes its canonical public location from the source-space address to the destination-space address. The public body, safe metadata, and permitted public navigation are unchanged unless the user separately changes them through their normal governed controls.
- A successful public move invalidates the former and destination public addresses, navigation, search, and page data. The former address may redirect only to the one current canonical address when the moved page remains public and published; otherwise it becomes unavailable without revealing the page.
- Draft, registered, restricted, Raw-source, audit, and protected provenance data remain outside anonymously readable representations during and after a migration.

### Key Entities

- **Cross-Space Migration**: A user-authorized operation that relocates one eligible page or a selected folder subtree between Wiki and AI Generation, with a preview, confirmation, status, and durable result.
- **Migration Selection**: The root page or folder, the included and excluded descendant pages, and the expected source state used to ensure confirmation acts on the reviewed content.
- **Destination Mapping**: The selected destination space and folder plus the resulting unique destination path for each moved page.
- **Migration Item Outcome**: The durable result for one selected page, including its former and resulting locations, completion state, adaptation, warning, conflict, or failure.
- **Classification Audit Record**: An immutable record that a user moved an imported or existing page into AI Generation; it distinguishes that decision from verified AI-generation provenance.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An authorized user can preview and complete a conflict-free single-page migration from either web entry in under 60 seconds, excluding time spent reviewing content.
- **SC-002**: A conflict-free folder migration preserves 100% of selected page identities, prior revision counts, and relative paths, with zero duplicate active pages at the source location.
- **SC-003**: In acceptance testing, 100% of conflicting, unauthorized, Raw, stale-selection, and visibility-escalating migration requests leave page content and public availability unchanged.
- **SC-004**: For every completed migration, authorized reviewers can retrieve a result identifying all selected pages and their outcomes, and unauthorized callers receive no protected page detail.
- **SC-005**: A public moved page's former address either reaches its one current canonical address or safely becomes unavailable; it never serves a second public copy of the page.
- **SC-006**: The documented external interface and MCP complete the same supported page and folder migration acceptance scenarios as the Navigator Pane with equivalent results and authorization outcomes.

## Assumptions

- This release supports migration only between the Wiki and AI Generation spaces. Raw remains a specialized, append-only evidence location and is not reclassified through this workflow.
- An eligible actor is an Administrator, including an appropriately authorized external API or MCP client acting for an Administrator; the existing writing mode controls whether AI Generation is available.
- A destination folder is supplied or selected by the user. Its default is the source path, which preserves the existing hierarchy when that path is free.
- Migration is organizational and does not itself publish content. Destination visibility defaults are used only when they do not broaden access; a more permissive result requires an explicit authorized decision.
- Existing Wiki.js-import metadata remains source evidence. Moving a page to AI Generation records a human classification and does not certify a specific AI model, prompt, or generator that was not captured at import time.
- Bulk migration uses the project's durable background-operation behavior when needed; it does not require the user to keep a browser tab open.

## Out of Scope

- Moving Raw pages into or out of Raw, changing Raw retention, or editing raw source material.
- Creating, publishing, or rewriting content merely because it is moved.
- Reclassifying content across separate deployments; archive and Wiki.js import remain the existing site-to-site migration paths.
- Bulk selection of unrelated pages from the Pages list; this release provides the requested per-page list action and folder-based bulk migration in Navigator.
